# ADR-0002: Ускорение Qwen через отдельный continuous-batching runner

- Статус: Предложен
- Дата: 2026-11-24

## Контекст
По данным инициатора: Ubuntu 24.04, Python 3.12, RTX 4060 Ti 8 GB, driver 595, torch 2.11 cu128, RAM 14 GB, свободный диск ~18 GB.
4071 frozen query, Qwen3-1.7B BF16 без LoRA/квантования; greedy, thinking=False, бюджет 2048 сохраняются.
HF batch=8 даёт ~400 query/h при GPU 96%, VRAM ~7 GB; это ~10,2 часа на полный набор с нуля.
Проверен `ml/gigabench/tools/qwen_batch.py`: один `generate` на left-padded batch, следующая группа ждёт завершения всей предыдущей.
`QwenAdapter` задаёт input_profile/chat template, проверяет snapshot fingerprint; helper проверяет metadata и пишет ответы по ID.
Текущий `--probe` измеряет восемь ответов, но не output tokens/s; для решения нужен отдельный сопоставимый probe.
ADR-0001 остаётся в силе; это дополнение, а не замена. `docs/requirements/` и `docs/context/` не обнаружены.
Совместимость пакетов и доступность API на целевом ПК здесь не проверялись; это проверяет основной исполнитель.

## Варианты
### A. Оставить HF batch=8
Нулевая стоимость миграции, известный resume, простой откат. GPU utilization не измеряет полезную работу: padding и ожидание длинного ответа сохраняются.
Можно группировать по длине входа, но она плохо предсказывает длину выхода; увеличение batch ограничено VRAM. Прирост не гарантирован.
### B. vLLM offline continuous batching в отдельном окружении
Освободившиеся слоты заполняются сразу; paged KV cache и специализированные kernels могут увеличить полезный throughput.
Средняя стоимость: новый runner и provenance; риски wheel/torch/CUDA, KV cache, RAM/диск, численные различия ответов. Откат прост: старое окружение и run неизменны.
### C. Transformers continuous batching
Меньше смена стека, потенциально переиспользуется tokenizer/input builder; отдельный runner и тесты всё равно нужны.
Выбирать только если установленная либо отдельно проверенная версия реально поддерживает Qwen3 BF16 и нужный CUDA backend/API.
Это не обычный `generate(batch)`; неподтверждённая поддержка/нестабильность делают вариант резервным, а не обещанным ускорением.

## Решение
Выбираем B условно: только после короткого probe и подтверждения совместимости. Без выигрыша или при проблемах — A; C проверять как резерв, не затягивая полный запуск.
Оценка для планирования, не измеренный результат: гипотеза 1,5–3× (~600–1200 query/h, ~6,8–3,4 часа на 4071).
При одинаково длинных ответах выигрыш от заполнения слотов меньше; GPU уже занят, поэтому обещать кратное ускорение нельзя.

### Память и параметры
- Начать с BF16, `max_model_len=4096`, `max_num_seqs=16`, `gpu_memory_utilization=0.85`, `enforce_eager=True`.
- До запуска токенизировать все frozen prompts тем же template: input tokens + 2048 должны помещаться в 4096. Иначе увеличить context и пересчитать память, не обрезать вход/выход.
- Веса занимают примерно 3,4 GB десятичных; остальное требуется KV cache, activations и runtime. Проверить фактическую конфигурацию модели и доступные KV blocks по логам.
- Для типовой конфигурации Qwen3-1.7B (28 слоёв, 8 KV heads, head_dim=128) BF16 KV ≈112 KiB/token, один context 4096 ≈448 MiB.
- Следовательно, 16/32 полных context одновременно в 8 GB не помещаются: `max_num_seqs` — потолок scheduler, не гарантия резидентности. Следить за preemption/recompute.
- Если старт стабилен, но KV cache ограничивает работу, проверить 0.90 при seqs=16; затем seqs=32 только при достаточном запасе и отсутствии thrashing.
- `enforce_eager` исключает CUDA graphs и связанный прогрев/память; точное отключение compilation проверить для выбранной версии. Цена — потенциально меньшая скорость.
- При OOM снизить seqs до 8 и ограничить prefill token batch поддерживаемым параметром; бюджет ответа не менять. Не включать CPU offload/swap без отдельной оценки 14 GB RAM.

### Минимальный согласованный probe
1. Заранее зафиксировать 20 одинаковых query ID, представляющих разные длины входа/типы задач; не отбирать по правильности. Все запуски получают тот же порядок.
2. Один snapshot/hash, BF16, input_profile, tokenizer/template и точные input token IDs; greedy (vLLM temperature=0), thinking=False, max_new_tokens/max_tokens=2048, одинаковые EOS/stop IDs.
3. Сверить effective generation defaults (penalties, stop strings, ignore_eos); не вводить новых stop rules. EOS может завершать ответ раньше, лимит не сокращать.
4. Последовательно, без конкурирующего GPU процесса: HF batch=8 и vLLM 16/0.85; одинаковый короткий warmup вне замера, startup отдельно.
5. Измерить wall time всех 20, сумму реально сгенерированных output tokens (единое правило учёта EOS, без padding), output tokens/s и query/h; сохранить peak VRAM, RAM, errors, stop reasons и raw IDs.
6. При успешном старте проверить 16/0.90, затем при необходимости 32; на 20 query последний вариант проверяет максимум 20 concurrent, насыщение 32 им доказать нельзя.
7. Сопоставить длины и тексты: greedy между engines не гарантирует идентичность. Разница query/h из-за более коротких ответов сама по себе не доказывает ускорение kernels.
8. Повторить победителя и HF на тех же 20, если разница мала. Предлагаемый порог перехода: ≥1,3× output tokens/s, отсутствие OOM/errors и регрессии wall time; иначе сохранить HF.

## Последствия
План developer:
1. Сохранить legacy checkpoint после корректной остановки/согласования responses hash и run metadata; не запускать два генератора одновременно.
2. Проверить wheel для Python 3.12/данной GPU и driver; отдельное env с зависимостями выбранного vLLM, не принуждать его к текущему torch 2.11. Не собирать из исходников как первый путь.
3. До установки оценить скачивание/распаковку и RAM: 18 GB диска может не хватить. Переиспользовать неизменяемый локальный snapshot, не удалять legacy env/ответы ради установки.
4. Реализовать отдельный offline runner с bounded queue, сохранением по завершённым ID, защитой от дублей, crash-safe metadata и resume только при совпадении engine/config/hash.
5. Провести probe; затем создать новый run с теми же 4071 frozen queries/cases и проверенными hashes, отдельным manifest/provenance без ослабления `verify`.
6. В новый run не переносить HF responses: полный vLLM прогон с нуля, отдельные результаты и backend/version/flags/template provenance. Probe не подмешивать в production responses.
7. Сравнить стоимость перехода: setup + 4071 / измеренный_vLLM_query_per_hour против оставшиеся_HF / 400. Если HF близок к финишу, миграция может задержать результат.
8. При отказе вернуться к исходному HF run/env; при выборе Transformers continuous batching применить тот же probe и правило отдельных run.

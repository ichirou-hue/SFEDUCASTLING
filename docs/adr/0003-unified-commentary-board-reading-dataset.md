# ADR-0003: Единый SFT-набор handoff и board_reading с числовой доской только для клеток

- Статус: Предложен
- Дата: 2026-11-26

## Контекст

Нужен один обучающий датасет из handoff и board_reading: numeric board только в задачах про клетки из **обоих** источников, полный FEN сохраняется. Для объяснений нужно сохранить исходные facts и метаданные, не превращая их без согласования в подсказки модели.

Проверены следующие границы:

- `ml/benchmark/tools/prepare_handoff_numeric_cells.py` читает frozen `handoff-desc-v1`, проверяет hashes/counts/tasks и создаёт новый каталог из трёх JSONL и manifest. Меняет только user content у `free_square` и `piece_on_square`; `move_commentary` копирует без изменений. Он не объединяет источники и не проверяет межисточниковые пересечения.
- `ml/dataset_generation/board_reading/numeric_board.py` — готовый общий formatter. `format_cell_query` выводит доску без state, но сам FEN не выводит. Кодировка: 0 — пусто; ±1…±6 — pawn/knight/bishop/rook/queen/king, плюс для белых; строки 8→1, столбцы a→h.
- `board_reading/build.py` создаёт `cell`, `track`, `check`, `attack`, `defense`, `material`, `legal_count`; исключает benchmark placements, включая промежуточные позиции последовательностей, и не повторяет использованные placements между splits. Numeric-режим **заменяет** FEN в prompt, хотя поле `fen` остаётся.
- `board_reading/data/pilot-cells-v1` содержит только `cell` и уже numeric prompts; `pilot-numeric-v1` — более широкий numeric-набор. Их нельзя просто склеить с handoff: требование сохранить FEN во входе ещё не выполнено, а numeric-only поведение вне клеток не соответствует новому контракту.
- `gigachess_data/s6_build.py` сохраняет комментарии в `commentary_v2.jsonl` (`question`, `answer`, `target`, `source`, `generator`, `group_id`), а `facts`, `draft`, `intent` и служебные поля — в `facts_v2.jsonl` с join по `id`. Facts включают engine-оценки; это не автоматически разрешённый модельный вход.
- `board_reading/train.py` читает только `messages`, маскирует user tokens и обучается на assistant answer. Ожидает ровно user/assistant и отказывает при длине свыше 512 токенов; остальные поля не подаются модели.

ADR-0001/0002 не заменяются. Файлы `docs/requirements/` и `docs/context/` при поиске не обнаружены. Frozen handoff и его facts в ходе точечного просмотра не найдены: фактический состав и полноту join необходимо проверить при сборке, не считать доказанными по коду экспортёра.

## Варианты

### A. Оставить наборы отдельными или склеить существующие JSONL

Минимальная стоимость и простой откат. Не закрывает единый формат входа, сохранность facts и межисточниковую split-гигиену; прежние проверки каждого источника недостаточны.

### B. Тонкий детерминированный сборщик поверх существующего SFT-формата

Один новый версионированный каталог, прежние `messages` и formatter, явные адаптеры двух источников. Невысокая сложность, дешёвые проверки без LLM/Stockfish, удобные тесты неизменности и откат к исходным каталогам. Нужны provenance, join facts и общий аудит splits. Выбираем.

### C. Новая унифицированная схема с генерацией объяснений и facts в prompts

Позволяет стандартизовать всё, но требует нового training/inference-контракта, дороже, меняет задачу и создаёт риск oracle leakage. Нельзя обосновать без подтверждения доступности facts при inference. Не выбираем.

## Решение

### Минимальный контракт

1. Выход: новый каталог с `train.jsonl`, `validation.jsonl`, `test.jsonl`, `manifest.json`. Исходники не перезаписывать. Каждая строка имеет уникальный `id`, исходные `task`, полный `fen` и `messages=[user, assistant]`; сохраняет все остальные исходные поля без потерь.
2. Коллизии ID разрешать namespace источника. Добавить отдельный объект `provenance` с dataset/source ID, исходными `id`, `split`, `group_id` (если есть), ссылкой на исходный файл. Не переписывать существующее поле `source`. При конфликте имён новых полей с исходными — отказ, а не молчаливое затирание.
3. Allowlist numeric-cell преобразования: handoff `free_square`, `piece_on_square`; board_reading `cell`. Не переименовывать исходные задачи ради общей схемы. `track` по умолчанию не считать статической задачей про клетку: решение о его включении в numeric-профиль требует уточнения.
4. Для allowlist user content: `Позиция FEN: {исходный fen}\n\n` + `format_cell_query({"fen": fen, "prompt": исходный вопрос})`. Использовать **один** существующий formatter и его SHA-256 для обоих источников. Не вычислять question из gold и не менять answer.
5. Для уже numeric cell-входа валидировать известную исходную форму, отделять исходный вопрос и строить канонический prompt заново: ровно один FEN и одна доска, без двойного добавления. Не применять произвольные эвристики к неизвестному prompt. Предпочесть проверенный FEN-источник, если он представляет ровно те же записи.
6. Для остальных задач numeric board не добавлять. Объяснения сохраняют messages/вопрос/ответ как в исходнике; никаких новых facts, target, verdict, draft или gold в user/system messages. Numeric-only не-клеточный источник отклонять либо брать его проверенный FEN-эквивалент; не переписывать такие prompts молча.
7. Facts и сопутствующие поля сохранять **в данных, не в модельном входе**. Уже встроенные поля копировать как есть; внешний `facts_v2.jsonl` присоединять по исходному ID в отдельное поле `source_facts_record`, сохраняя весь объект и ссылку/hash sidecar. Требовать однозначного join для включённых объяснений; пропуск/конфликт — ошибка или явно согласованный неполный выпуск, но не выдуманные facts. Если facts уже находились в исходных messages, остановиться для уточнения, а не молча удалить или считать разрешёнными.
8. Manifest фиксирует версию схемы и профиля, hashes всех источников/manifest/sidecars/formatter/сборщика, allowlist, `facts_in_messages: false`, seed и порядок, количества по source/task/split, SHA-256 и число строк выходов, исключения и результаты проверки пересечений. По умолчанию каждую принятую строку включать один раз, без oversampling и скрытой балансировки.

### Split-гигиена

- Сохранять исходные splits, не делать случайный resplit объединённых строк и не переносить validation/test в train ради пропорций.
- Проверять объединение **после** адаптации: исходная группа/партия при наличии и ключ расстановки `chess.Board(fen).board_fen()` не могут пересекать splits. Namespace у групп предотвращает случайное совпадение ID, но не заменяет глобальное сравнение placements между источниками.
- Для комментария учитывать также известный `fen_after`; для последовательностей — начальную, промежуточные и конечную позиции. Связанные по группам или позициям записи проверять как одну компоненту, включая транзитивные связи.
- Повторно сверять все включённые позиции с явно заданными frozen benchmark cases и их последовательностями. Hash benchmark каждого родителя не заменяет проверку общего набора; фиксировать конкретные проверенные benchmark hashes.
- При конфликте split, дубле записи, конфликтующем ответе на одинаковый вход или benchmark overlap — по умолчанию отказ с перечнем source IDs и причин. Не удалять/перемещать строки скрыто. Согласованные исключения применять целыми связанными группами и отражать в manifest; отсутствие пересечений нельзя обещать до аудита реальных источников.
- Внутри одного split несколько разных задач на одной позиции допустимы; точные дубли не должны неявно менять вес примера. Test используется для финальной оценки, не выбора смеси/параметров.

### Открытые вопросы пользователю

1. Какие конкретно frozen handoff (и sidecar facts) и board_reading брать: только `pilot-cells-v1` или полный набор? Для полного набора: считать ли `track` «задачами про клетки»? До ответа не расширять allowlist.
2. Правильно ли, что «сохранить facts» означает сохранить их как поля датасета, **не** добавляя в messages? Это безопасное предлагаемое поведение. Для facts-conditioned обучения нужно отдельно подтвердить список доступных при inference фактов и новый профиль оценки; oracle engine facts нельзя подмешивать по умолчанию.

## Последствия

Сохраняются существующий trainer-формат, formatter и исходные ответы. Новая инфраструктура, генерация ответов и запуск движка не нужны. Цена — аудит источников/sidecars, возможный отказ сборки при конфликте и более длинные клеточные prompts. Сохранённые facts не означают, что модель на них кондиционируется.

План для developer:

1. Зафиксировать конкретные источники и ответы на вопросы выше; проверить manifests, hashes, формы сообщений и наличие facts.
2. Сделать тонкие адаптеры и единый сборщик; использовать существующий formatter, контракт numeric-cell преобразования handoff и новый выходной каталог.
3. Провести lossless join и общий аудит групп/placements/benchmark. При конфликте вынести список на согласование, не менять исходники.
4. Проверить тестами: FEN присутствует во входе обоих cell-источников; ровно одна доска; вопрос/assistant/объяснения/метаданные неизменны; facts не попадают в messages; корректны namespace и join; неизвестные формы, hashes и split-конфликты дают отказ; повторная сборка детерминирована.
5. Токенизировать весь набор целевым tokenizer/template перед обучением. FEN+numeric может превысить текущий лимит 512: не обрезать FEN, вопрос или ответ; согласовать увеличение лимита trainer либо явно учтённые исключения. Это проверка совместимости, не повод менять содержание датасета.
6. Выпустить manifest и сводку source/task/split, после успешного аудита обучать по `messages` с assistant-only loss. На inference применять тот же профиль FEN+numeric только к согласованным cell-задачам.

ADR описывает предложение, не подтверждает готовность или фактическую чистоту объединённого набора. Откат — использование неизменённых исходных наборов.

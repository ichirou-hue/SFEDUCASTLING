# ADR-0004: Независимые профили модели, входа и набора бенчмарка

- Статус: Предложен
- Дата: 2026-11-27

## Контекст

Нужны профили прогона для Qwen и GigaChat без смешения модели, способа подачи позиции и размера набора. Действующий код — `ml/benchmark`, Python-пакет внутри него называется `gigabench`. Отдельный staging и текущий GPU-эксперимент `qwen-four` на ПК не входят в область изменений: не обновлять его код, окружение, настройки, входы или ответы, не останавливать и не перезапускать.

Точечный просмотр выявил:

- `run.py`: `--profile=smoke|quick|standard` управляет подготовкой набора, `--input-profile` выбирается отдельно, но default зависит от backend. Есть только `gigachess`, `qwen`, `mock`; GigaChat API здесь не реализован.
- `gigabench/adapters.py`: `input_builder` поддерживает `question_only`, `contract_v1_fen` и Python callable. Для callable сохраняется hash одного файла, но не импортированных зависимостей и не всего фактического входа.
- `GigaChessAdapter` использует локальные `gigachess_runtime.Runtime` и `run_candidate_interface.generate`; передаёт FEN **отдельным аргументом** даже при `question_only`. `config.generation.profile` — runtime-профиль `candidate_rank_major_start7`, не профиль набора и не шаблон текста. Называть этот backend GigaChat API нельзя.
- `QwenAdapter` использует HF Transformers и snapshot fingerprint; `tools/qwen_vllm.py` — другой backend с тем же builder и Qwen chat template, thinking=False. vLLM сохраняет chat/input IDs и запрещает resume с иной identity.
- `tools/qwen_vllm_numeric_trio.py` также обслуживает четыре модели при `--mixed-adapter`: фиксирует `standard`, бюджеты 512/2048 и профиль `fen_numeric_static_cells_v1`; FEN есть всегда, numeric board добавляется только к статическим клеточным задачам. Общие входы и hashes обеспечивают matched-сравнение base/LoRA. Это специализированный эксперимент, не универсальный профиль Qwen.
- `tools/compare_reports.py` проверяет равенство cases/queries/config/code, извлекает input identity по подстрокам `profile`/`builder`, сравнивает весь `engine`. При этом не включает `numeric_inputs_sha256` как самостоятельное доказательство идентичности фактических запросов. Равенство имени профиля недостаточно, а равенство scheduler-настроек излишне для сравнения качества разных backend.
- `run.py compare` вызывает **другой** модуль, `gigabench/comparison.py`: он допускает разные input profiles и вычисляет paired deltas. Два способа сравнения сейчас имеют разные контракты.

Прочитаны ADR-0001–0003; это дополнение, а не замена их решений. `docs/requirements/` и `docs/context/` при поиске отсутствуют. Доступность GigaChat API, конкретная модель, авторизация, параметры генерации и возможность закрепить версию **не подтверждены**. ADR не разрешает платные запросы и не предполагает API-доступ.

## Варианты

### A. Оставить как есть, добавить ещё один model-specific скрипт

Минимальные затраты сейчас, текущие прогоны не затрагиваются. Однако растёт число неявных defaults, названия профилей остаются неоднозначными, два comparator продолжают давать разные гарантии. Тесты и аудит усложняются; требования сопоставимости не закрыты.

### B. Тонкий версионированный run spec поверх существующих freeze и runner

Разделить независимые настройки, материализовать запросы до inference, применять общий контракт сравнения. Небольшая стоимость JSON-артефактов и hashing, без нового оркестратора и без смены scoring. Хорошо тестируется без GPU/API; откат — прежние неизменённые прогоны. Главный риск — неполный учёт скрытых входов backend, поэтому вводятся явные уровни сопоставимости. Выбираем.

### C. Универсальный inference gateway и новая схема всего бенчмарка

Единый API для локальных моделей и сервисов, но большие изменения pipeline, resume и упаковки; риск нарушить исторические результаты. Производительность gateway не решает основную проблему. Дорого, пока нет подтверждённого GigaChat-интерфейса; не выбираем.

## Решение

### Разделение и минимальные поля

В новых прогонах сохранять один разрешённый `run_spec.json`, а не создавать комбинации вида «gigachat-standard» как независимые реализации. Именованные presets допустимы только как ссылки на составные настройки; перед запуском все defaults раскрываются.

| Раздел | Минимальное содержимое |
|---|---|
| Оболочка | `schema_version`, идентификатор прогона, `comparison_mode`, ссылки/hashes frozen manifest и родительского прогона при наличии |
| `model` | `id`, revision или явное `unknown`, fingerprint локальных weights/tokenizer и LoRA при наличии; для API — запрошенный ID и фактически сообщённая версия, если доступна |
| `backend` | `id`, версия/хэш runner, версии библиотек, effective runtime options; для GigaChess — отдельно `runtime_profile` и runtime/codec hashes |
| `suite` | `id=smoke|quick|standard`, `version`, freeze manifest/cases/queries hashes, упорядоченные selected IDs, stage и явные включения/исключения источников/задач |
| `input` | `id`, `version`, декларация доступных полей/каналов, template/builder и hashes зависимостей, параметры форматирования, hash материализованных запросов |
| `generation` | фактические sampling/thinking/stop настройки, seed или явное отсутствие поддержки, бюджет по query, отображение этих настроек на backend и неподдерживаемые поля |
| `scoring` | версия схемы метрик, hashes scorer/config/rubrics и judge identity (версия, сеть, бюджет), если применимо |

Не все backend поддерживают одинаковые поля: отсутствие поддержки — явно, не подстановка фиктивного `False` или `0`. Пути, timestamps, auth tokens не входят в идентичность содержания. Секреты не сохранять и не хэшировать в публикуемых артефактах.

- Suite не зависит от модели. `smoke/quick/standard` определяют генерацию/состав, но одинаковое имя **не доказывает одинаковые задачи**; сравниваются frozen данные. `--limit` — сегмент исполнения, не новая случайно уменьшенная suite. Явная подвыборка должна быть заморожена заранее.
- Input не меняет gold, scoring или вопрос. Numeric/FEN форматирование использует только разрешённые публичные поля, включая task metadata для allowlist. Не передавать builder весь case с gold. Engine facts разрешены только отдельным заранее согласованным профилем с доказанным источником при inference.
- Backend отвечает за исполнение и модельную сериализацию; input — за содержимое/каналы запроса. Например, `contract_v1_fen@1` можно подавать разным моделям; `question_only@1` вместе с дополнительным FEN-каналом GigaChess не равен одному текстовому вопросу.
- Предлагаемые backend IDs для новых specs: `qwen-transformers`, `qwen-vllm`, `gigachess-runtime`; `gigachat-api` — зарезервированное имя, **не готовая интеграция**. Старые metadata/CLI не переименовывать на месте.

### Versioning, материализация и resume

1. Версия схемы и версии suite/input независимы. Изменение смыслового контракта создаёт новую версию; изменение реализации или зависимости фиксируется hash даже при прежнем имени. Версия без hash не является доказательством.
2. До inference создать неизменяемый `requests.jsonl`: query ID, ordered messages с ролями, все дополнительные модельные каналы, бюджет и effective generation policy. Сохранять точный текст без trim/нормализации Unicode. Для локальных моделей отдельно сохранять rendered chat и input token IDs с hashes tokenizer/template. Для API — фактический отправляемый payload без секретов; не выдумывать серверный chat template.
3. Зафиксировать canonical JSON алгоритм: UTF-8, sorted object keys, compact separators, без NaN, с сохранением порядка массивов и точных строк. Hash каждого нормализованного request и всего упорядоченного набора; отдельно SHA-256 байтов файлов для контроля целостности. Параметр модели и транспортные request IDs не входят в общий межмодельный content hash, но входят в provenance исполнения.
4. Поддерживать два fingerprint: **resume identity** (модель, backend/код/окружение, входы, suite, generation) и **comparison identity** (контракт измерения по правилам ниже). Не требовать совпадения модели для сравнения; не разрешать её смену для resume.
5. Ответ связан с query/request hash, содержит finish reason, доступные usage/error сведения. Ошибки и not_run остаются в знаменателях ADR-0001; retries только транспортные по фиксированной политике, не «пока ответ правильный».
6. При изменении или недоказуемости resume identity — новый каталог. Для API без закрепляемой версии отмечать ограниченную воспроизводимость; неизвестную серверную ревизию нельзя считать доказательством её неизменности.

### Два режима сравнения

**`matched` — строго одинаковые запросы на доступной границе.** Требуются одинаковые frozen cases/gold/queries, selected IDs и stage, точные сообщения/дополнительные каналы для каждого ID, бюджеты и сопоставимая effective generation policy, одинаковый scoring/judge, полное покрытие и проверенные hashes ответов. Имена профилей сами по себе ничего не доказывают.

- Для одной модели/tokenizer при смене HF/vLLM дополнительно требовать одинаковые rendered chat и input token IDs. Scheduler и engine implementation могут различаться: это отражается как сравнение backend, а не скрывается. Greedy не обещает одинаковых ответов.
- Для разных моделей/tokenizer совпадают точные сообщения на клиентской границе, но не обязаны совпадать token IDs. Отчёт явно указывает `equality_scope=client-messages`; разные токенизаторы делают равный лимит токенов неравным объёмом текста/compute. Не называть такое сравнение побитово одинаковым модельным входом.
- Скрытый system prompt API или недоступная сериализация означают отсутствие доказательства одинакового полного модельного входа. Если неизвестны/различаются даже эффективные generation controls или дополнительные каналы, строгий режим отклоняется. GigaChess с отдельным FEN/codec нельзя автоматически приравнять к plain chat API.

**`model-native` — разные входные профили на одинаковых задачах.** Только явный opt-in, без автоматического fallback из `matched`. Те же cases/gold, selected IDs, scoring и полные знаменатели; различия messages, FEN/numeric/codec, generation budgets и backend показываются отдельной таблицей. Результат характеризует связку **модель + профиль + runtime**, не изолированный эффект модели/LoRA. Δ допускаются как описательные, в отдельном отчёте, не в общей matched-таблице. Изменение самих вопросов/gold/состава задач — уже не этот режим.

Оба entry point сравнения должны использовать один validator и печатать причины отказа/уровень гарантии. Исторические отчёты не переписывать. Для legacy без достаточных доказательств выводить `unverified`, не достраивать hashes из имени профиля и не объявлять strict-эквивалентность.

### Открытые вопросы пользователю

1. Под GigaChat имеется в виду внешний API или имеющийся локальный GigaChess runtime? Если API: какой разрешённый endpoint/model ID, есть ли доступ и согласие на отправку benchmark-данных? Секреты в чат не нужны.
2. Нужен прежде всего matched baseline на общем FEN-входе, model-native оценка каждого runtime или оба раздельных отчёта?
3. Какие источники/задачи включать в smoke/quick/standard: legacy, экспертные объяснения, 300 M4–M7-auto? Какие бюджеты расходов, времени и output tokens согласованы? Не переносить автоматически специальные условия `qwen-four` на GigaChat.
4. Для Qwen нужен обычный FEN-профиль или также FEN+numeric для статических клеток; какие snapshot/LoRA сравнивать в **новых** прогонах?

## Последствия

Профили переиспользуются без размножения скриптов, исчезает неоднозначность слова `profile`, сравнения получают проверяемую область гарантий. Цена — материализация входов и небольшой объём дополнительной metadata; генерация не ускоряется и API-паритет не обещается. Полный fingerprint weights уже применяется и остаётся отдельной затратой. Откат прост: старые runners и артефакты остаются неизменными.

План для developer:

1. Согласовать вопросы выше; никаких API/GPU запусков до разрешения. Исключить staging `qwen-four` из выкладки.
2. Добавить resolver/validator новых specs, сохранив старые flags как совместимый вход; `--profile` трактовать как suite, `runtime_profile` — отдельно. Добавить dry-run с resolved spec и таблицей capabilities.
3. В новых каталогах материализовать запросы и fingerprints; переиспользовать существующие builders, не менять содержимое frozen queries. Извлекать специализированный numeric-профиль только для будущих запусков, не рефакторить работающий staging.
4. Подключить общий comparator к обоим entry point с явным режимом; не ослаблять `verify` глобально. Новые scoring fingerprints внедрять версионированно, не подменять старые `code_sha256`.
5. Проверить без GPU/API: детерминированность materialization; смена одного пробела/роли/FEN-канала/budget ломает matched; смена модели допустима для сравнения, запрещена для resume; одинаковый profile name с разным входом отвергается; native требует opt-in; разные IDs/gold/scoring, неполнота и missing hashes не проходят strict.
6. После подтверждения конкретного GigaChat API отдельно проверить документацию/capabilities, лимиты и политику данных; только затем реализовать adapter и согласованный smoke в новом каталоге. При отсутствии доступа оставить интеграцию неподключённой, не подменять её GigaChess.

# ADR-0001: Достаточный бюджет Qwen и раздельная оценка ответа

- Статус: Принят; основной контракт реализован, ограничения перечислены в отчёте
- Дата: 2026-11-24

## Контекст
Исправляем существующий GigaBench, не создаём новую систему.
По данным инициатора, GPU baseline Qwen3-1.7B: 4071 ответ, 3601 обрезан, 3202 без prediction; аудит 20 ответов: 13 не успели завершиться, 1 правильный choice отвергнут, 6 действительно неверных. Эти числа здесь независимо не перепроверялись.
Развёрнутый ответ и исчерпание бюджета не доказывают шахматную ошибку.
В `ml/gigabench/gigabench/` парсеры отделены от `compliant`, но `score_case` обычно превращает отсутствие prediction в `correct=False`; отчёты используют это как «неверно».
`pipeline.prepare` замораживает бюджеты в cases/queries; `verify` проверяет также текущий код; отдельный `rescore` уже копирует исходные данные в новую папку.
`tools/qwen_batch.py` использует бюджет query, greedy chat и `enable_thinking=False`; обычный QwenAdapter также уже отключает thinking/sampling.
Существующих ADR и файлов требований в `docs/requirements/` при поиске не обнаружено.

## Варианты
### A. Оставить как есть
Нет затрат и изменений воспроизводимости; дешёвая генерация. Но короткий лимит и строгий разбор смешивают ошибки измерения с ошибками содержания; требования не закрыты.
### B. Достаточный фиксированный бюджет + детерминированное извлечение
Небольшие изменения текущих config/CLI, parser/scorer/report; проверяемые правила и обратимость через отдельные артефакты. Генерация потенциально дороже, часть естественных ответов останется неоднозначной.
### C. LLM judge или повторные запросы только для нераспознанных
Больше восстановленных ответов, но дополнительная система, стоимость и недетерминизм; выборочные повторы меняют условия сложных примеров. Не выбираем.

## Решение
Выбираем B. Вопросы пользователя, FEN, варианты выбора, gold и состав задач не меняются. Не добавляем требования краткости и не переписываем ответы модели.

### Генерация
- Для новых Qwen-прогонов добавить `generation.qwen.max_new_tokens=2048`; CLI `--max-new-tokens` допускает, в частности, 1024. Это единый заранее выбранный бюджет, не автоматические повторы по результату.
- Разрешать CLI override только при создании нового freeze; сохранять разрешённый бюджет в queries/cases и manifest. Не подменять значения на resume.
- Новую выборку получать копированием исходных cases/queries с изменением только бюджета и новым manifest, а не повторным построением gold; сохранить связь с исходным freeze.
- Сохранить текущие chat/input_profile, `enable_thinking=False`, `do_sample=False`, `num_beams=1`; EOS завершает ответ раньше лимита. Не обрезать сохранённый текст.
- Записывать effective budget, output token count и stop reason (`eos`, `length`, `error`, `unknown`); `length` означает достигнутый лимит, а не доказанно незавершённый смысл.
- Manifest/run фиксируют generation policy и её hash, model/tokenizer/template, runner hash (включая batch helper), версии и execution segments. Greedy не обещает битовой идентичности между GPU/batch.

### Извлечение содержания
- Сохранить парсеры коротких ответов, добавить общий ограниченный recovery явного итогового блока (`Ответ:`, `Итоговый ответ:`, `Final answer:`), затем типизированный разбор payload.
- Контракт извлечения: только text, score_type и публичные параметры вопроса/FEN. Gold доступен лишь следующему этапу сравнения; целевая клетка piece берётся из вопроса/params, не из `gold['square']`.
- Возвращать значение, источник/позицию фрагмента и причину отказа. Длина текста сама по себе не влияет на правильность; format проверяется отдельно на исходном тексте.
- Для bool/int/choice/judgement извлекать одно явное значение допустимого типа; для piece — цвет/тип или явную пустоту на запрошенной клетке; для move_set — явно завершённый список, включая пустой.
- Для move извлекать заявленный UCI/SAN, затем проверять легальность по FEN отдельно. Явный нелегальный UCI — неверное содержание, а не отсутствие ответа; не выбирать среди кандидатов по легальности или gold.
- Для mate_move явное «нет» — полноценный prediction отсутствия мата, а не null; сравнение с gold выполняется после извлечения.
- Не выбирать последнюю встреченную букву/число/ход из рассуждений. Список вариантов, цитата вопроса, отрицание кандидата, гипотеза и конфликтующие итоговые ответы не дают prediction.
- Явная финальная формулировка может следовать после обсуждения других вариантов; при нескольких противоречащих итоговых блоках — ambiguous, без угадывания. Незавершённый итоговый payload не восстанавливать.
- Обрезание после уже законченного однозначного ответа не отменяет его оценку; открытый/оборванный список ходов не считать законченным.

### Оценка и знаменатели
- Добавить `content_correct: true|false|null` и `answer_status`: `answered`, `ambiguous`, `unparseable`, `no_answer`, `budget_without_answer`, `execution_error`, `not_run`; engine/coach pending остаются отдельным состоянием оценки.
- `budget_without_answer` = лимит достигнут и нет извлечённого ответа; формулировка отчёта не утверждает, что дополнительный бюджет обязательно исправит результат.
- Минимально сохранить `correct` как индикатор подтверждённого успеха для агрегатов: false при отсутствии ответа, но UI «неверно» выводить только по `content_correct=False`.
- Главный показатель — подтверждённо верные / все заранее включённые случаи соответствующей автоматической задачи. Не удалять unparseable, budget, errors и not_run из знаменателя; это нижняя оценка успешности, не доля доказанных шахматных ошибок.
- Сохранять заранее определённые области engine/mate/coach, показывать их отдельными группами; не исключать случаи по результату парсинга. Для balanced accuracy и bootstrap использовать тот же полный состав и классы, включая not_run.
- Дополнительно: conditional content accuracy среди оценённых ответов (только диагностическая), answer coverage, execution coverage, доли формата, лимита, отсутствия ответа и подтверждённых ошибок; везде показывать n/N.
- При неполном прогоне сохранять запрет публикации итогового automatic macro; таблицы показывают полный знаменатель и пометку partial. Нельзя улучшить основной балл отбрасыванием сложных ответов.

### Freeze, rescore и resume
- Старые freeze/ответы/отчёты не менять; старые лимиты остаются историческими. `rescore --source ... --out NEW` пересчитывает только сохранённый текст, не достраивает обрезанные ответы и не выдаётся за новый inference.
- Не ослаблять `verify` глобально. В rescore отдельно проверять hashes cases/queries/responses, связь run→manifest, уникальность/допустимость IDs; сохранять scoring version, hashes нового кода/config и исходных артефактов.
- Stored engine verdict переиспользовать только при совпадающем prediction и проверенной provenance исходных scores/engine; иначе требовать движок, не переносить старый вердикт на новый ход.
- Оба генератора проверяют единую generation policy и эффективные бюджеты перед append. При несовпадении либо отсутствии необходимой metadata с существующими ответами — отказ, новый каталог; никогда не молчаливые новые defaults.
- Для исторического resume допустим только явно воспроизведённый старый контракт/код, не смешение 32 и 2048 токенов. Rescore-каталог не использовать для продолжения генерации.

## Последствия
Минимальный план developer:
1. Добавить Qwen budget config/CLI и freeze-clone с проверкой неизменности всех полей кроме бюджета; унифицировать metadata/resume проверки pipeline и batch helper.
2. Добавить recovery и типизированные причины, отдельно от gold/compliance; сохранить полный raw и извлечённый фрагмент.
3. Обновить scoring/агрегаты/HTML/Markdown: содержание, формат, причины отсутствия ответа, coverage и честные знаменатели; версионировать схему результата.
4. Проверить adversarial cases: длинный верный/неверный ответ; обсуждение A/B с явным итогом C; «не A»; цитируемый `Ответ: A`; конфликт двух итогов; пустой список против обрыва; нелегальный ход; SAN/UCI; отрицание мата; чужая клетка piece; EOS на границе бюджета; лимит до/после ответа; error и not_run.
5. Проверить независимость извлечения от подмены gold, неизменность источника rescore, отказ resume при смене бюджета/template и невозможность роста основного балла от потери prediction; затем rescore старого baseline и отдельный полный прогон 2048.
Стоимость — больше времени генерации и несколько явных полей результата; новая инфраструктура/LLM judge не нужны. Откат — предыдущий scoring и исходные неизменённые артефакты. Старые и новые бюджеты не сравнивать как один и тот же эксперимент.

## Реализация

Актуальный контракт и метрики:
`docs/ml/2026-11-24-answer-first-benchmark.md` и `ml/gigabench/METRICS.md`.
Промежуточные отчёты реализации удалены при очистке по просьбе пользователя.
Не заявляется полная реализация каждой расширенной рекомендации:
неоднозначность пока входит в `unparseable`, нелегальный ход может не распознаться,
отрицание мата отображается отдельной веткой при `predicted=None`,
target square остаётся метаданными исходного case. Это не выдаётся за
подтверждённую ошибку модели. Новый набор подготовлен тем же детерминированным
генератором; неизменность cases/gold проверена SHA-256 относительно исходного.

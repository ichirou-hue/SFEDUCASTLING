# Ревью: четыре Qwen-модели и автоматическая проверка комментариев

Diff: `git diff`, `git diff --staged`; для перенесённого `train.py` — сравнение с `HEAD:ml/dataset_gen/board_reading/train.py`; новые untracked-файлы проверены целиком · Вердикт: ⚠️ после правок 🔴

## Находки

- 🔴 `ml/benchmark/gigabench/commentary.py:624–632` — SAN проверяется только по получившемуся UCI. `python-chess.Board.parse_san()` не валидирует истинность суффикса шаха/мата: в начальной позиции `e4+` и `e4#` разбираются как `e2e4`. Поэтому «Сыгран e4#» получает подтверждённый move claim, хотя мата нет; отдельный распознаватель русского слова «мат» здесь не поможет. Это ошибочное подтверждение факта в M4 и пропуск критической ошибки M6. Предложение: отдельно проверять заявленные `+`/`#` по доске после хода либо создавать check/mate claims; добавить тесты ложных и настоящих суффиксов. Отсутствие суффикса у настоящего шаха не обязательно считать ошибкой.
- 🟡 `ml/benchmark/tools/run_qwen_four_models.sh:47–54` — проверяется связь mixed → source manifests, но не связь training manifests → фактически выбранные benchmark cases. В manifests уже есть `benchmark_cases_sha256` и `commentary_benchmark_cases_sha256`, однако они не сравниваются с подготовленным набором. `load_frozen_suite()` проверяет самосогласованность файлов, а не совпадение с набором, использованным при исключении утечек из обучения. При замене согласованного frozen suite можно запустить сравнение с неподтверждённой защитой от утечки. Предложение: до обучения сверять оба benchmark hash из всех трёх manifests с архивом и frozen commentary suite, проверять 300 commentary cases; повторять проверку для metadata адаптеров при прямом запуске runner.
- 🟡 `tests/ml/gigabench/test_qwen_vllm_numeric_trio.py:18–46` — новый протокол покрыт тестами форматирования и списка моделей, но нет CPU-only интеграционного теста `prepare()` и пути generation → scoring → comparison для четырёх моделей. Не проверяются также старый режим без `--mixed-adapter`, отклонение чужого training metadata и resume с изменёнными hashes. Предложение: добавить тест подготовки реального архива во временный каталог с проверкой 8357 + 300 и неизменности исходников; inference заменить stub, проверить четыре summary и `comparison.json`, отдельно три прежние метки и профиль. Это позволит проверить контракт до дорогого GPU-запуска.

## Что хорошо

- Оригинальный архив читается, новый набор записывается отдельно; его 8357 cases закреплены константным SHA256, queries дополнительно сопоставляются с cases.
- Для всех четырёх моделей строится один набор токенизированных входов. FEN сохраняется везде, numeric добавляется только четырём явно перечисленным статическим cell tasks; state tracking исключён.
- Факты комментария сохраняются в исходном prompt. Автоматические M4–M7 остаются отдельными метриками.
- Старые labels и `numeric_board_v1` сохранены для режима без mixed adapter; новые labels распознаются существующим механизмом именования отчётов.
- Есть fingerprints весов и адаптеров, checksums входов, проверка параметров при resume и контроль целостности завершённых responses.
- В последней прочитанной версии launcher проверяет существование общего lock, открывает его без усечения и держит `flock` на протяжении обучения и оценки. Один локальный snapshot передаётся в обучение и inference.
- `--max-length` не обрезает ответы молча: превышение лимита останавливает обучение; metadata сохраняет лимит и основные параметры.

## Границы проверки

Широкий перенос папок не оценивался как изменение этой задачи. Во время ревью `train.py` и launcher обновлялись параллельно; учтены добавленные `--snapshot` и проверка существующего lock. GPU и SSH не запускались. Попытка независимо запустить CPU unittest отклонена разрешениями shell; заявленные 40 успешных тестов самостоятельно не перепроверены. SAN-находка установлена по логике кода и контракту `parse_san`, не отдельным выполненным тестом. Полный end-to-end на GPU не подтверждён.
